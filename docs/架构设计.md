## 2. 一轮对话的时序

```
浏览器                chat_service            LangGraph           工具/存储
  │  POST /api/chat       │                      │                   │
  ├──────────────────────►│                      │                   │
  │                       ├─ 取/建会话 ───────────────────────────────►│(MySQL)
  │                       ├─ 载入历史+摘要 ──────────────────────────►│
  │                       ├─ 解析模型(有无图片?)                       │
  │                       ├─ 长期记忆召回 ───────────────────────────►│(Qdrant)
  │                       ├─ 落库 user message ──────────────────────►│
  │◄──ssse: start─────────┤                      │                   │
  │◄──ssse: memory_recall─┤                      │                   │
  │                       ├─ graph.ainvoke ─────►│                   │
  │◄──ssse: node(plan)────┤                      ├─ 规划 LLM ───────►│
  │◄──ssse: plan──────────┤                      │                   │
  │◄──ssse: node(act)─────┤                      ├─ 决策 LLM ───────►│
  │◄──ssse: tool_start────┤                      ├─ 执行工具 ────────►│
  │◄──ssse: tool_end──────┤                      │  (异常转 ok:false)  │
  │◄──ssse: node(act)─────┤  (回到 act 再决策)     │                   │
  │◄──ssse: node(answer)──┤                      ├─ 流式生成 ────────►│
  │◄──ssse: token × N─────┤                      │                   │
  │                       ├─ 演示可用性判定(demo.py)                   │
  │                       ├─ 落库 assistant message ────────────────►│
  │◄──ssse: demo──────────┤                      │                   │
  │◄──ssse: done──────────┤                      │                   │
  │                       └─ 后台：滚动摘要（超阈值时）                 │
```

要点：

- **SSE 而不是 WebSocket**：服务端单向推送足够，实现简单、断线可重连。
- **事件驱动渲染**：前端 `stores/app.ts::handleEvent` 按事件类型增量更新，
  所以用户能看到「计划已生成 / 正在调用工具 / 第 2 步完成」的实时过程。
- **落库与推送解耦**：先落库再发 `done`，前端收到 `done` 后重新拉一次消息列表，
  保证刷新页面后内容一致。

## 3. 数据模型

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `users` | id, username | 本地单用户，预留 `X-User-Id` 多用户扩展 |
| `provider_configs` | provider, base_url, **api_key_enc**, model, vision_model, is_active | 模型接入配置；`api_key_enc` 是 Fernet 密文 |
| `conversations` | id(uuid), title, provider, model, summary, message_count, pinned | 会话；`summary` 存滚动摘要 |
| `messages` | conversation_id, role, content, plan, demo, tool_calls, tool_results, tokens, latency_ms | 消息，含 Agent 轨迹快照与演示判定结果 |
| `memory_items` | kind(fact/preference/profile/goal/skill), content, importance, access_count, indexed | 长期记忆 |
| `knowledge_docs` | title, source, tags, content, char_count, chunk_count | 知识库原文（向量在 Qdrant） |
| `agent_runs` | plan, steps, status, iterations, latency_ms | 可观测性：一次 Agent 执行的完整记录 |
| `screen_sessions` | goal, plan, status, interval_ms, current_step, dry_run | 屏幕演示会话（`current_step` 是续跑关键） |
| `screen_steps` | session_id, idx, thought, action, status, screenshot | 每一步的思考/动作/截图 |
| `app_settings` | key, value(JSON) | 运行参数持久化（重启后恢复） |

### Qdrant 集合

| 集合 | 向量维度 | payload |
| --- | --- | --- |
| `code_knowledge` | 512（可配） | doc_id, title, source, tags, chunk_index, text |
| `long_term_memory` | 512 | memory_id, content, kind |

- 点 ID 用 `uuid5(namespace, "kb:{doc_id}:{chunk_index}")`，重复入库是覆盖而非新增。
- 维度变化时 `ensure_collection` 会重建集合并打警告，需要点一次「重建索引」。

## 4. LangGraph 状态图

```python
class AgentState(TypedDict, total=False):
    plan: dict                 # 规划器输出
    tool_messages: Annotated[list[BaseMessage], operator.add]  # 累加
    iterations: int            # 已执行轮数
    has_tool_calls: bool       # act 是否要求调工具
    answer: str                # 最终回答
```

| 节点 | 职责 | 出错时的行为 |
| --- | --- | --- |
| `plan` | 调规划模型，解析 JSON 计划 | 解析失败 → 用兜底计划；调用失败 → 提示 + 兜底计划 |
| `act` | 带工具绑定的模型决策：需要工具就返回 `tool_calls` | 调用失败 → 提示 + 跳过工具 |
| `tools` | 逐个执行工具，转成 `ToolMessage` | 工具异常 → 捕获后包成 `{ok:false}` |
| `answer` | 带证据流式生成最终答案 | 失败 → 友好错误 + 兜底文案 |

条件边：`act --has_tool_calls and iterations<max--> tools`，否则 `answer`；
`tools --> act` 形成闭环，`recursion_limit = max(8, max_iterations*3+6)` 防止死循环。

**为什么规划与回答要用两次模型调用？**
规划用低温（0.2）保证结构化稳定，回答用 0.5 保证表达自然；
更重要的是「先承诺计划、再执行」这个过程本身就是要展示给学习者看的。

## 5. 关键设计取舍

### 5.0 时延优化：先减跳数，再减每跳成本

慢的根因是**串行模型往返次数**，不是代码本身。优化按收益排序：

1. **工具并行**：`tools_node` 用 `asyncio.gather` 跑完所有 tool_calls，耗时从「求和」变「取最大」。
2. **少走一轮**：`tools → answer` 直连（轮次用尽时不再问模型"要不要调工具"），固定调用数 4 → 3。
3. **快车道**：寒暄跳过 plan 与 act；短概念题跳过 plan，并把 `knowledge_search` 作为
   「直达工具」直接调起（不调模型），调用数降到 1~2。
4. **客户端复用**：`build_chat_model` 进程内缓存 `ChatOpenAI`，复用连接池，省掉重复 TLS 握手。
5. **瘦身**：规划器 JSON 模式 + `max_tokens=500`；answer 的证据 1500 → 420 字/条。
6. **预算**：`agent_budget_s` 超时即收口，`agent_tool_rounds` 控制工具轮次上限。

### 5.1 为什么统一走 OpenAI 兼容协议

DeepSeek、通义千问（DashScope compatible-mode）、Ollama（/v1）、LM Studio、one-api
都实现了 `/chat/completions`。用 `ChatOpenAI(base_url=...)` 一个类就能全部覆盖，
新增厂商只需在 `llm/registry.py` 加一条数据，无需写适配器。

**模型列表不写死**：`GET /models` 是 OpenAI 兼容协议的标配，所以下拉框里的候选是运行时拉取的
（`POST /api/providers/{id}/models`，带 60s 缓存），与内置推荐合并后再做多模态能力推断（按 `vl`/`vision`
等命名特征）。厂商上新模型、账户被灰度到新模型，都不需要改代码；拉不到就回退推荐并允许手填。
这样也避免了「写死的清单落后于厂商发布节奏」这类问题。

### 5.2 为什么去掉了内置 mock 模型

早期版本内置了一个 `mock` 供应商，用来在没有 Key 的环境里跑通全流程。实际用下来它的害处大于好处：
它返回的是**写死的假回答**，看不出检索质量、看不出工具调用是否真的生效，验收时反而会误导人。
所以现在默认供应商是 `deepseek`，没配 Key 时界面直接提示去配置；要零成本体验就用本机 Ollama
（`llm/service.py` 走同一套 OpenAI 兼容协议），或者智谱 `glm-4-flash` 的免费额度。

### 5.3 为什么默认离线哈希向量

`sentence-transformers` 需要下载几百 MB 模型，教学环境经常被墙。
哈希向量（中文 1~2 字滑窗 + 英文标识符 → blake2b 哈希到 512 维 + L2 归一化）
对「词面重合度高」的中文技术问答召回效果够用，且零依赖、结果确定。
再叠加关键词重合度重排，实际检索质量可接受（`docs/screenshots/08` 的检索调试可直接看到分数）。
需要更强语义时，`EMBEDDING_PROVIDER=api` 切到 `text-embedding-v3`。

### 5.4 屏幕控制的坐标与输入

- **归一化坐标 (0~1000)**：提示词要求模型输出归一化值，执行时按实际分辨率还原，
  换显示器/改分辨率不用改提示词。送给模型的截图还会叠加 10×10 网格与刻度，
  视觉模型直接读刻度比凭感觉估点准得多；存盘给界面看的是无网格原图。
- **快捷键优先**：`actions.py` 支持单键、组合键（`win+r` / `alt+tab` / `ctrl+shift+p`）、
  批量 `sequence`、拖动、滚轮。系统提示词内置「Win+R 打开程序、Alt+Tab 切窗口、
  Ctrl+Shift+P 命令面板」这类工具箱，并明确要求「能用快捷键就别猜坐标」——
  这是提升成功率最大的一招。
- **中文输入与输入法**：pyautogui 只能打 ASCII，而且模拟按键要先过输入法——中文模式下敲
  `print("hi")` 很容易变成全角、丢字或被候选框吃掉回车。三层防护：
  ① 文本一律走剪贴板 + Ctrl+V（`screen_type_mode=clipboard`），输入法完全不参与；
  ② 落键前把代码里的全角标点纠正成半角（`normalize_input_text`，只对看起来像代码的文本生效）；
  ③ 演示期间用 Win32 IMM 把前台程序临时切英文、结束还原（可关）。
  实测新式程序（Edge/VS Code）走 TSF，`ImmGetContext` 拿不到上下文，所以 ①② 才是主防线。
- **容错**：非法键名 / 缺坐标会被 `normalize_action` 拦下并降级成 `wait`，
  同时把原因写进 thought；模型把 action 写在顶层也能解析。
- **防呆与经验沉淀**：每一步都用「下一帧画面变没变」判卷——变了记为有效做法，没变记为无效并
  进入本次会话的禁用表，第二次出现直接跳过（指纹按 100×100 像素归一，抖动几十像素算同一个动作）；
  连续 3 次无效自动暂停。经验按前台应用分域存进 `screen_lessons` 表，下一轮以
  「已验证有效，优先复用 / 已验证无效，不要再试」回灌提示词；用户在对话里说的操作指示
  （"用 Ctrl+Shift+P 打开命令面板"）也会被提取成经验。提示词同时声明「预设步骤只是参考路线」，
  避免模型为了按步骤走而反复踩同一个坑。
- **安全**：`pyautogui.FAILSAFE=True`（鼠标移到左上角中止）、默认演练模式、
  最大步数上限、动作白名单，提示词里还禁止删除/格式化/关机等破坏性操作。

### 5.4.1 智能体之间为什么要共享上下文

对话智能体看不见屏幕，屏幕智能体不知道对话里聊了什么，两边各自做决策就容易"隔空喊话"。
共享层只解决一件事：**让任何一侧的观察结果两边都能用**。

- 通道是 `screen_agent/context.py`：`set_observation / get_observation / render_context`，
  存摘要文本 + 截图路径，不存原始像素；
- 对话侧通过 `look_at_screen` 工具主动"看"，屏幕侧在每轮决策时被动读；
- 用 TTL（5 分钟）和限流（8 秒）控制新鲜度与开销——过期的观察宁可不给，
  否则模型会拿着旧画面编指令；
- 观察只做客观描述，不做操作建议，避免两套决策逻辑互相干扰。
### 5.4.2 文件工具为什么是只读的

给智能体文件权限很容易变成事故：一次误判就可能删掉源码。所以这里把边界定成：
**能读、能定位、能打开，不能写**。

- 代码层面没有提供任何写入/删除/重命名函数，`open_path` 还额外拦截 exe/bat/ps1/lnk；
- 能不能"改"由屏幕演示负责——键盘鼠标在真实界面里操作，学习者看得见、随时能暂停，
  出错也只影响当前这一步；
- 白名单 + 系统目录拒绝 + `resolve()` 后再判断，三层挡住越权访问；
- 提示词里写死「要改文件必须走屏幕演示」，防止模型自作主张。

这样既解决了"屏幕智能体找不到文件只能乱点"的问题，又不会把文件系统变成不可控的写入口。

### 5.4.3 提示知识为什么独立于向量库

知识库原本只有一种东西：文档，切块进向量库，靠语义检索按需召回。但「怎么做事」这类内容是
**每轮都该生效**的约束，不该等检索命中——搜不到就等于没有。

所以加了 `kind=guide` 的第二类条目：

- 不进 Qdrant（`chunk_count=0`），不参与语义检索，避免污染知识召回；
- 按 `target`（chat / screen / both）直接拼进对应智能体的系统提示词；
- 改动后 `invalidate_cache()` 让 20 秒缓存立即失效，下一轮即生效。

配套的「本机环境画像」也走这条路：启动时采集一次系统信息写成 `guide`，
解决模型默认用 Linux 写法回答 Windows 问题的老毛病。

### 5.5 错误处理的三层防线

1. **工具层**：`try/except` → 结构化 `{ok:false,error,hint}`
2. **编排层**：`tools_node` 再包一层 `try/except`；节点失败降级继续跑
3. **接口层**：`AppError` → 统一 JSON；`RequestValidationError` → 422；
   兜底 `Exception` → 500 且带 `hint`，前端弹 toast

对应 `core/errors.py`、`agent/tools/builtin.py`、`agent/graph.py`、`main.py` 的异常处理器。

### 5.6 环境管家：为什么安装要跑在后台线程里

装一个 JDK 动辄几分钟，HTTP 请求等不起。所以 `/api/env/install` 只做三件事：
校验入参、登记任务、起线程，然后立刻返回 `job_id`；真正的 winget / 下载 / 解压在这个线程里跑。

```
POST /api/env/install ──► InstallManager.start() ──► Thread(_run)
                                    │                    │
                                    └── job 快照 ◄────────┤ 逐行 append 日志
                                                         └─ _finish: 找 exe → 写 PATH → 验证 → 切终态
浏览器 ── GET /install/{id}?since=N ──► snapshot(N)：只回增量，轮询很轻
```

几个踩过的坑，都写进了实现：

1. **进度条不是换行**。winget 用 `\r` 刷新进度，按 `\n` 切只会拿到一行；
   这里按 `\r\n|\r|\n` 切分二进制流，再按 utf-8 → gbk → latin-1 依次解码（中文 Windows 常见）。
2. **终态要最后置**。收尾（找 exe、写 PATH、跑 `--version` 验证）如果发生在 `status=succeeded`
   之后，前端一看到终态就停轮询，正好把收尾日志和结果漏掉 —— 所以 `_finish()` 先跑完再赋值。
3. **安装程序自己也会改 PATH**，但改的是注册表。不把注册表 PATH 同步回本进程，
   「装完立刻验证」必然失败，看起来像安装失败。
4. **别把 PATH 写坏**。改之前备份到 `data/env_path_backup.json`，写回时保留原类型
   （`REG_EXPAND_SZ` 写成 `REG_SZ` 会把 `%USERPROFILE%` 固化掉），最后广播 `WM_SETTINGCHANGE`
   让新开的终端认得。
5. **同一时间只跑一个任务**。两个安装程序同时改 PATH 很容易互相覆盖，所以第二个请求直接
   返回 409 + `ok:false`，前端提示排队。

装完的目录按三档找：现成 PATH → 安装根目录（`--location` 装进去的）→ 常见默认位置
（`%LOCALAPPDATA%\Programs`、`%ProgramFiles%`、winget 的便携包目录），都带时间预算和深度上限。

```
├─ Composer.vue              自适应输入 / 图片上传 / 模式切换 / 停止生成
├─ AgentPanel.vue            可拖拽宽度的右侧面板
│  ├─ panels/TracePanel.vue      计划、工具、节点时间线、演示判定
│  ├─ panels/MemoryPanel.vue     长期记忆 CRUD + 召回测试
│  ├─ panels/KnowledgePanel.vue  文档入库 / 检索测试 / 重建索引
│  └─ panels/ScreenPanel.vue     演示状态摘要
├─ SettingsModal.vue         模型接入（Key 加密保存/测试/切换）+ 运行参数
│                           外观 / 编辑器快捷键库 / 环境管家（检测·一键安装·默认打开方式）
└─ ScreenModal.vue           演示控制台（实时画面 + 步骤时间线 + 间隔滑杆）
```

主题切换：`ui.theme`（light / dark / auto）→ `document.documentElement.dataset.theme`，
偏好写 `localStorage`；「跟随系统」时监听 `prefers-color-scheme` 变化自动重绘。

状态管理用 Pinia 三个 store：`app`（会话/模型/流式）、`screen`（演示会话）、`ui`（弹窗 + 主题）。

设计系统在 `styles/global.css`：CSS 变量定义配色/圆角/阴影，**深色与浅色两套令牌**——
`html[data-theme="light"]` 只覆盖表面、文字层级、阴影与强调色，组件样式零改动即可换肤；
代码块在两种主题下都保持深色底，保证语法高亮对比度。
`.markdown` 完整排版规则，代码块带工具条与复制按钮（`utils/markdown.ts`）。
